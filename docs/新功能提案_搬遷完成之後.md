> **實作進度**（2026-08-12）：

## 為什麼會有這份文件

PolyMigrate 解的是 **Phase 1 → Phase 2**：把舊站鏡像下來，抽成 frontmatter Markdown，
配對雙語，產出轉址表。這一段做得完整，`verify` 也把品質保證做成了產品。

但香雲寺專案在那之後還發生了三件事：

1. 內容被灌進 CMS、部署上雲、對外開放
2. **舊站沒有停止更新**——並行期間持續有新文章
3. 上線後才發現一個「產出物完全正確、但網站上找不到」的頁面

第 1 項是 CMS 專屬的，不該進 PolyMigrate（見末節「刻意不做的事」）。
第 2、3 項則是**任何搬遷案都會遇到**的，而且目前沒有工具解。

## 先承認一件事：`fetch-orphans` 已經夠用

香雲寺專案這次補抓新文章時，另外寫了一支 `crawl/fetch_new.py`——
指定 slug、抓所有語言版本、連資產一起抓。

這與現有的 `polymigrate fetch-orphans <config> --section news --slugs <file>` **功能重疊**。
是先寫了才發現工具已經有，屬於重造輪子。

**所以下面的提案刻意避開已有功能**，只列真正的缺口。

> 第二版補記：這段自承除了「避免重複造輪子」之外，還是一個更重要的訊號——
> **連作者自己都會忘記工具有什麼功能**。這對「該不該再加三個指令」本身就投了一票，
> 詳見〈換角色看〉的「第一次用的人」。

## 提案一：孤島頁面偵測（`verify` 的擴充）— 優先做

### 問題

香雲寺的 BLIA Austin 頁面在上線後「從網站上消失」。實際狀況是：

| 檢查項目 | 結果 |
|---|---|
| 頁面檔案存在 | ✅ |
| frontmatter 欄位完整 | ✅ |
| 內文、圖片、雙語齊全 | ✅ |
| `verify` | ✅ 全過 |
| 上線後全站巡檢 584 頁 | ✅ 0 錯誤 |
| **實際上找得到嗎** | ❌ **完全找不到** |

原因：它是頂層頁面，沒有任何其他頁面連到它，選單裡也漏了它。
**沒有任何入口 = 對訪客而言不存在。**

更要命的是**巡檢也抓不到**——因為巡檢是沿著連結走的，
走不到的頁面根本不會被走訪，於是回報「584 頁全部正常」。
「零錯誤」在這裡是誤導：它證明的是「連得到的頁面都正常」，
不是「所有頁面都正常」。

### 為什麼 PolyMigrate 適合做這件事

**不用碰網路就做得到**，完全符合 `verify` 現有的設計原則：

```
輸出頁面集合  −  被任何頁面連到的集合  =  孤島頁面
```

`verify` 已經在掃內部連結（香雲寺實測 1,269 個），
等於**必要的資料已經在手上**，只差反向求一次差集。

> 第二版查證：比這裡寫的還便宜。`OutputVerifier.Run()` 已經用 `BuildRoutes()` 建好
> 「所有輸出頁面」的集合，逐一連結比對的迴圈也已經在跑 `NormalizeRoute(reference)`，
> **只是比完就把結果丟掉**。實作等於在該迴圈旁多累積一個 `HashSet`，跑完求差集，
> **不需要新增任何一趟掃描**。

### 建議行為

```sh
polymigrate verify out/
  ...
  warning: 1 page is not linked from anywhere:
    en/blia/index.md   (orphan — reachable only by typing the URL)
```

判定為 **warning 而非 error**：有些頁面本來就刻意不連（隱私頁、活動報名的到達頁），
但作者應該要「知道自己有這種頁面」，而不是不知不覺。

可用 config 指定豁免清單：

```yaml
verify:
  allow_unlinked:
    - en/thanks/index.md
```

> 第二版修正（實作時採用）：**豁免清單沒有放進 config**，改為 `--allow-unlinked <檔案>`。
> 理由是 `verify` 的「只讀輸出、不需 config、不碰網路」是它的設計前提（`PolyMigrator.Verify`
> 的簽章就沒有 config），為了一份豁免清單破例並不划算。清單改成純文字檔，
> 一行一頁、`#` 註解，內容相對路徑或路由皆可。

> 第二版補充（實作前必須解掉，否則這功能會反傷）：
>
> - **首頁一定被誤判成孤島**——沒有人會連回站根路由。多語站則是「每個語言的首頁」
>   都會中槍。必須內建豁免，否則每次跑都跳警告。
> - **`verify` 看不到選單**。它只掃內文與 frontmatter `images[].local`，
>   導覽列不在掃描範圍。所以工具能誠實斷言的是
>   「**沒有任何內容頁**連到它」，不是「完全沒有入口」。BLIA 這案剛好兩者都成立，
>   但輸出訊息的措辭要跟得上這個界線，否則只是換一種形式的過度信任。
> - **warning 會改變 exit code**，這是最大的地雷，見〈換角色看〉的「在 CI 裡跑的人」。

### 價值判斷

這是三項裡**投入最小、抓到的問題最難自己發現**的一項。
`verify` 的行銷主軸是「0 錯誤成績單」——但成績單如果漏掉一整類錯誤，
反而會讓人過度信任。補上這一項，那張成績單才誠實。

## 提案二：增量同步（`diff` / `sync`）

### 問題

搬遷不是一次性的。新舊站並行期間，舊站會繼續更新，
必須反覆同步到 DNS 切換為止。香雲寺專案這次就發現舊站多了 4 篇新聞、1 個活動。

目前的做法是人工的：抓列表頁 → 用正規表示式挑出 slug → 跟本地檔名求差集 → 再手動餵給 `fetch-orphans`。
**每次都要重寫一次一次性的比對腳本。**

### 與 `probe-orphans` 的差別

兩者容易混淆，但解的是相反方向的問題：

| | `probe-orphans` | 提案的 `diff` |
|---|---|---|
| 方向 | 往回挖**被移除索引**的歷史文章 | 往前找**新增而本地還沒有**的文章 |
| 手段 | 依日期規則逐日探測 URL | 讀現在的列表頁，跟本地求差集 |
| 時機 | 搬遷當下，補齊歷史 | 搬遷之後，持續追平 |

### 建議行為

```sh
polymigrate diff <config.yaml> --section news
  old site: 218 pages   local: 231 pages
  missing locally (4):
    20260731  20260727  20260726  20260716

polymigrate sync <config.yaml> --section news     # diff + fetch + extract 一條龍
```

`diff` 只讀不寫，可以進 CI 或排程——**並行期間每天跑一次，舊站一發新文就知道**。

### 需要 config 支援

列表頁的位置與 slug 樣式因站而異，需宣告：

```yaml
sections:
  news:
    index: "/{lang}/news/index.php"
    slug_pattern: '(\d{8}[A-Za-z]?)\.php'
```

香雲寺的活動沒有列表頁（`/ch/events/index.php` 回 404），是從首頁卡片連出去的——
所以 `index` 必須允許指到任意頁面，不能假設每個 section 都有自己的列表頁。

> 第二版查證與修正：
>
> - **成本被低估。** `SiteConfig` 目前**沒有 `sections:` 這個頂層區塊**；section 的概念
>   散在 `extract.section_types` 與 `extract.section_flags` 兩個以目錄名為 key 的字典裡。
>   這是開一個新的頂層設定分類，還要決定它與既有兩個字典如何共存，屬於契約變動，
>   不是「加欄位」。
> - **通用性最弱。** 它假設舊站還活著、有列表頁、slug 有規律。而上一段自己就承認
>   活動沒有列表頁——**這個假設在同一個站內部就已經破了一次**。
> - **結論改為砍半實作**，只做本地那一半，見〈第二版建議順序〉。

## 提案三：全尺寸媒體最佳化（`thumbs` 的姊妹）

### 問題

`thumbs` 產生的是**額外的小預覽圖**（`media/` → `media_thumb/`），原檔不動。
但搬遷完幾乎一定還要做另一件事：**把原檔本身換成適合網頁的尺寸**。

香雲寺的實測數字：

| | 檔數 | 大小 |
|---|---|---|
| 原檔（相機直出，最大 8256×5504） | 2,231 | **4.92 GB** |
| 網頁版（長邊 1920 / JPEG q82 / 去 EXIF） | 2,231 | **1.19 GB（24%）** |

4.92 GB 直接上雲的代價是真實的：儲存費、部署時間、前台載入速度。
而且在本案的上傳頻寬（實測 1.5 Mbps）下，這個差別是 **7 小時 vs 1.8 小時**。

### 關鍵設計：檔名不能變

壓縮後**檔名與相對路徑必須完全一致**，Markdown 裡的媒體引用才不用改。
這也是不建議轉 WebP 的原因——副檔名一變，所有引用都得跟著改。
（香雲寺實測：JPEG 佔 96%，轉 WebP 大約再省 25–30%，
但要重寫 2,172 筆引用，投入與收益不成比例。）

### 建議行為

```sh
polymigrate optimize <config.yaml> [--max-long-edge 1920] [--quality 82]
  4.92 GB → 1.19 GB (24%)
  2,180 recompressed · 51 copied as-is · 0 failed
```

幾個從實作中學到的細節值得內建：

- **壓完反而變大就用原檔**（小圖、已優化過的圖很常見；本案 51 個）
- **EXIF 轉正後再存**，並去除 EXIF（含 GPS 等個資）
- **非圖片一律原樣複製**（mp4、PDF、GIF 動畫）
- **失敗時退回原檔而不是跳過**——寧可大也不能缺
- 輸出到**另一個目錄**（`media_web/`），原檔是唯一保存檔、隨時可重產

> 第二版結論：**不做，改為文件。** 數據與上面那五條實作心得都是對的、也很有價值，
> 但價值在**知識**而不在程式碼——見〈刻意不做的事〉。

# 第二版：換六個角度重新檢驗

第一版只問了一個問題：「這個問題真不真實？」三項的答案都是真的，所以三項都通過了。
下面換六把不同的尺再量一次。

## 角度一：這件事需要 PolyMigrate 手上獨有的資料嗎？

這是最能一致解釋「什麼該進來、什麼不該」的一把尺。

| 提案 | 需要獨有資料嗎 |
|---|---|
| 孤島偵測 | **需要。** 頁面清單 + 連結圖只有 `verify` 手上有，外部工具做不到 |
| `diff` | **一半需要。** 本地 slug 集合是獨有的；抓舊站列表誰都能做 |
| `optimize` | **完全不需要。** 給任何人一個資料夾都能壓，PolyMigrate 沒有資訊優勢 |

末節用「CMS 專屬知識會讓邊界糊掉」排除了 CMS 匯入，這個理由很好。但同一把尺量下去，
`optimize` 也該被排除——它進來的理由是「搬遷完幾乎一定要做」，
可是「搬遷完幾乎一定要灌 CMS」也一樣成立。兩者真正的差別只是**有沒有綁定特定廠商**，
不是**屬不屬於搬遷**。

**第一版混用了兩把尺**：對 CMS 用「廠商中立」，對 `optimize` 用「常見需求」。
統一成上面這把尺之後，`optimize` 應該跟 CMS 匯入放在同一節。

## 角度二：壞掉的時候長什麼樣

比「對的時候多有用」更值得先想。

- **孤島偵測誤報** → 警告疲勞。若首頁、語言選擇頁、各 section 列表頁每次都跳警告，
  人只會加一堆豁免或乾脆不看，**結果是稀釋掉整個 `verify` 的可信度，比不做更糟**。
  所以內建豁免不是加分項，是必需品。
- **`diff` 安靜地失效** → 最危險的一種。舊站改版、列表頁 HTML 一變、regex 抓不到，
  它會每天乖乖回報「沒有新文章」。你以為在追平，其實早就斷了。
  排程任務最要命的失敗就是安靜地回報一切正常。
  要救的話，「抓到 0 篇」本身必須是 error 而不是 0 差異。
- **`optimize` 失敗** → 第一版已經想到了（退回原檔、寧可大也不能缺）。
  三者裡失敗模式設計最完整的一個，諷刺的是它也是最不該做的一個。

## 角度三：n=1 的通用性

三個提案全來自同一個專案。哪些真的「任何搬遷案都會遇到」？

- **孤島偵測**：純圖論，跟站別、語言、CMS 全無關。100% 通用。
- **`diff`**：假設最多、且該假設在香雲寺內部就破過一次（活動無列表頁）。通用性最弱，
  卻要加最多設定。
- **`optimize`**：通用，但那是「網站有照片」的問題，不是「搬遷」的問題。

## 角度四：這功能能活多久

- **孤島偵測**：每次跑 `verify` 都有用，**永久**。
- **`diff`**：只在並行期有用。DNS 一切過去，這段程式碼就再也不會被執行——
  但你要永遠維護它、永遠讓它在 CI 綠燈。**價值幾個月，成本無限期。**
- **`optimize`**：每個專案用一次。

`diff` 是最容易變成死代碼的一個，偏偏又是唯一需要連網 + 排程 + 對抗舊站改版的。

## 角度五：契約與版號的壓力

README 白紙黑字寫著 **CLI 介面與 Phase 輸出契約自 1.0 起未變**，
`contracts.md` 也寫「破壞性變更才升 major」。三個提案對這個承諾的壓力不同：

- **孤島偵測**：`verify_report.csv` 欄位不動，只多一種 issue kind 值。文義上屬 minor。
  **但實際行為上會咬到 CI 使用者**，見下一節。
- **`diff`**：要開新的頂層 config 區塊。舊 config 不會壞（新欄位選填），
  但 `config_version` 目前被 loader 硬鎖在 1，要先想清楚新區塊算不算 schema 變更。
- **`optimize`**：產出全新的輸出目錄，等於新增一份 Phase 契約，`contracts.md` 要加一整節。
  **契約表面積擴張最大，換來的是一個 `mogrify` 一行就能做的事。**

## 角度六：產品敘事

README 的一句話定位是 **the i18n-first static-site migrator**，
而且已經在賣「誠實」——`honestly reports what it cannot pair`。

- **孤島偵測長在這條敘事上。** 它不是新賣點，是**兌現既有承諾**：
  `verify` 現在的「0 錯誤」有一整類系統性盲區。用這個角度看，
  它比較像修 bug，不像加功能。
- **`diff` 與 `optimize` 都是往「維運工具」擴張**，會把那句銳利的定位稀釋掉。
  一個工具講不清楚自己是什麼，是很貴的代價。

# 第二版：換角色看——誰會被這些改動影響

上面六個角度都是從「工具本身」出發。這一節換成從**人**出發：
同一個改動，落在不同的人身上是完全不同的感受。

## 一、在 CI 裡跑 `verify` 的人 ← 最重要，會被咬

`Cli.cs` 的 `verify` 結尾是：

```csharp
return report.Errors > 0 ? 2 : report.Warnings > 0 ? 1 : 0;
```

**warning 會讓 exit code 變成 1。** 而目前唯一存在的 warning 種類是
`known_missing_media`，也就是說**大多數專案現在的 `verify` 是 exit 0**。

一旦孤島偵測以 warning 落地，這些人升級之後：

- shell script 裡的 `set -e` 會**直接中斷**
- CI 的綠燈變紅燈，而他們**什麼都沒改**

在使用者眼裡這就是破壞性變更，不管 `contracts.md` 把契約定義成什麼。
CSV 欄位沒變不代表沒事——**exit code 也是契約，而且是最多人依賴的那個**。

更糟的是第二層：`verify` 目前只把 `Severity.Error` 印到畫面上，
warning 只會出現在摘要的計數與 CSV 裡。所以升級後的第一次體驗是——
**exit 1、畫面上卻沒有任何一行告訴你為什麼**，得自己去翻 `verify_report.csv`。

處理方式（建議三件一起做）：

1. **內建豁免做足**（首頁、各語言首頁、列表頁），讓正常專案的孤島數是 0，
   絕大多數人升級後不會有感
2. **把 warning 明細也印出來**，不要只有計數
3. **CHANGELOG 明講**：升級後 `verify` 可能出現 exit 1，並附上
   `verify.allow_unlinked` 的用法

## 二、把 `PolyMigrate.Core` 當 .NET 函式庫用的人

README 提到 2.0 才剛把 `Cornhsu.PolyMigrate.Core` 的公開 API 收斂到預期的入口點，
所以這群人是存在的。對他們來說：

- `VerifyReport` 加屬性 → 相容，不痛
- `VerifyIssue.Kind` 多一個字串值 → 自己 `switch` 的話會落到 default 分支
- **如果他們是自己判斷 `Errors > 0` 才算失敗，孤島 warning 對他們完全無感**

這裡有個有趣的不對稱：**同一個改動，CLI 使用者會痛，函式庫使用者不會。**
因為痛的來源不是資料，是 `Cli.cs` 那行 exit code。
這也反過來說明：真正該小心設計的是 CLI 那一層，不是 Core。

## 三、第一次拿到 PolyMigrate 的人

目前的指令是 5 個：`extract`、`thumbs`、`probe-orphans`、`fetch-orphans`、`verify`。
三個提案全做就變 8 個，**CLI 表面積增加 60%**。

前面〈先承認一件事〉那段是最好的證據：**作者本人都會忘記 `fetch-orphans` 存在，
還另外寫了一支 `fetch_new.py`。** 每多一個指令，其他每個指令被找到的機率就下降一點。

對照之下，孤島偵測**不增加任何指令**——它是既有指令裡多一行輸出，
新使用者的認知成本接近 0。這在「新功能」裡是很罕見的性質，值得優先兌現。

## 四、真的要去修那個孤島頁的人（可能不是工程師）

他收到警告之後能做什麼？**修正的位置根本不在 PolyMigrate**，
而在網站的選單或 CMS 的導覽設定。所以訊息不能只說「這頁沒人連」，
要說清楚**後果**與**該去哪修**。

第一版寫的 `reachable only by typing the URL` 這句很好——白話、講後果、不講術語。
但如果一次跳出 20 個孤島（多語站的每個語言首頁、每個列表頁都算），
他會直接放棄看。**這再次指向「內建豁免是必需品」。**

## 五、接手維護這個 repo 的人

測試成本三者差距極大：

- **孤島偵測**：純函式，準備一棵假的 `content/` 樹就能測，零外部依賴，
  完全吃得下現有的測試風格
- **`diff`**：要 mock 網路或存舊站 HTML 當 fixture，而**那份 fixture 會腐化**——
  舊站一改版它就變成歷史文物，測的是三年前的網站長什麼樣
- **`optimize`**：要 binary 圖片 fixture，而 Magick.NET 的編碼結果跨平台、跨版本
  不保證位元一致，golden test 很脆，CI 多平台跑尤其會飄

## 六、正在評估要不要採用 PolyMigrate 的人

他只會做兩件事：讀 README 第一句，然後看指令清單。

「the i18n-first static-site migrator」＋ 5 個一眼看懂的指令，是一個清楚的東西。
加上 `diff` / `sync` / `optimize` 之後，它變成「一個搬遷器，外加一些維運雜工」——
**更難一句話講完，也更難相信它每一項都做得好。**

---

## 刻意不做的事

**CMS 匯入不該進 PolyMigrate。**

香雲寺後來把內容灌進 Umbraco，寫了約 1,000 行的匯入程式。但那是 CMS 專屬的：
內容類型、資料型別、語言變體、發布快取——換一套 CMS 就要整個重寫。

PolyMigrate 的定位是「輸出**乾淨、有契約、可被任何東西消費**的中間格式」。
把某一套 CMS 的知識放進來，會讓工具的邊界糊掉，也讓契約變得不穩定。

真要做，該做的是**文件**：「拿到 PolyMigrate 的輸出之後，怎麼餵給常見的 CMS」，
而不是把 CMS 的邏輯吃進工具。

**（第二版新增）全尺寸媒體最佳化也不該進來。**

理由用同一把尺：**PolyMigrate 在這件事上沒有任何獨有資料**。
壓縮 `media/` 只需要「一個裝滿圖片的資料夾」，不需要路由表、不需要連結圖、
不需要語言配對——`mogrify` 一行就能做完。

而它要付的代價是實的：新增一份 Phase 輸出契約、一組跨平台會飄的 golden test、
以及讓「i18n 搬遷器」這個定位多長出一隻維運的手。

提案三裡那些實作心得——壓完變大就用原檔、EXIF 轉正後去除、非圖片原樣複製、
失敗退回原檔而非跳過——**價值在知識，不在程式碼**。
它們應該和 CMS 匯入指南並列，寫成一頁〈搬完之後你還要做的事〉。

## 建議順序

### 第一版的結論（保留供對照）

| | 提案 | 投入 | 理由 |
|---|---|---|---|
| 1 | **孤島頁面偵測** | 小 | 資料已在手上、不碰網路、抓的是最難自己發現的一類錯 |
| 2 | **增量同步 `diff`** | 中 | 補上「搬遷全程」的最後一段；需要 config 新欄位 |
| 3 | **媒體最佳化 `optimize`** | 中 | 價值明確但可被外部工具替代，優先度最低 |

### 第二版的結論

| | 提案 | 決定 | 理由 |
|---|---|---|---|
| 1 | **孤島頁面偵測** | **照做** | 六個角度沒有一個反對；不增指令、不碰網路、測試最便宜 |
| 2 | **增量同步** | **砍成一半** | 只做本地那一半，見下 |
| 3 | **媒體最佳化** | **不做** | 移入〈刻意不做的事〉，改寫成文件 |

**提案二的砍法**：只有 PolyMigrate 手上有的資料是「本地已經有哪些 slug」，
那就只做這件事：

```sh
polymigrate slugs out/ --section news
```

純本地、不連網、不需新 config、不需排程、**不會安靜失效**。
「抓舊站列表」那一半留給使用者那 30 行腳本——因為那一半本來就因站而異，
硬要 config 化就會撞上「活動沒有列表頁」那種例外。
**拿到八成價值，付零成本的連網與維護。**

### 三項的共同點仍然成立

**都是搬遷「完成之後」才會遇到的問題。**
PolyMigrate 目前的範圍停在「產出正確的中間格式」，
而真實的搬遷案在那之後還有一段路——這三項是那段路上最先撞到的三塊石頭。

差別只在於：**其中兩塊石頭，繞過去比搬開它划算。**
